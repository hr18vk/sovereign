## §1. Context

The engine's observability has two layers, designed in ADR-0023 to be INDEPENDENT:
1. **The prometheus bridge** (`pkg/metrics/telemetry_bridge.go`) — a `prometheus.Collector` reading the 12 distinct `internal/telemetry` `*Counter` objects CUMULATIVELY via `Counter.Value()`, registered into the per-process `metricsExp.Registry()`, scraped via `/metrics`. Operated Day-18 onward.
2. **The OTel layer** (`internal/telemetry` registry + the `Int64ObservableCounter` callbacks) — reads each counter DELTA via `lastReported` on the collector's cadence. DOCUMENTED NO-OP Day-18: `telemetry.Init` had ZERO production callers, so the package-level Meter stayed nil (the synchronous-nop default) and no observable was ever registered.

ADR-0023 §6.2 named TWO landmines on the OTel layer, disclosed carry-forwards, explicitly left for "the future fork that arms Init":
- `init()` builds `QueryL0ListCapped` twice (the orphaned first object);
- `rebuildCounters()` builds `QueryL0ListCapped` zero times — so an `Init(realMeter)` call would reassign the var to nil → the use-site guard `query.go:253` silently stops counting the cap-hit disclosure counter.

Day-21 IS that future fork. It (a) dedups the `init()` construction (2 → 1), (b) FILLS `rebuildCounters()` (0 → 1), (c) arms `telemetry.Init(realMeter)` at boot in `cmd/sovereign-node` with a real `go.opentelemetry.io/otel/sdk/metric` `MeterProvider` (deps in `go.sum` v1.43.0; `go.mod` tidied to promote indirects — §0.b), gated `--otel` (the OTel-OFF research node keeps the Day-18 bridge-alone behavior), and (d) unblocks the `T_gc` auto-inference P1 (ADR-0020 §6a) — NOT implemented (the operator still sets `T_gc`; Day-20 contract).

## §3. The dedup mechanism + the two-exporter separation (decided BEFORE code)

**The dedup (§1.1):** in `init()`, DELETE one of the two `QueryL0ListCapped = newCounter(m, ...)` blocks (they were byte-identical — delete one; keep a SINGLE block). In `rebuildCounters()`, ADD the SAME single construction at the ANALOGOUS position (after `MemTableFlushTotal`, before `OffHeapAllocatedBytes` — matching `init()`'s order so the registered-instrument order under the OTel Meter is STABLE across the two construction sites; a drift in order is a registered-instrument-order drift observable to a collector — disclosed here). The prompt's §1.1 DRY-shared-ctor refactor was REJECTED (a single shared ctor would be a refactor; minimal-blast-radius is two literal constructions — the SAME pattern the other 11 counters ALREADY use).

**The two-exporter separation (§0.d refreshed):** `armOTel` (`cmd/sovereign-node/otel.go`) constructs a `sdkmetric.NewMeterProvider` with a `sdkmetric.NewPeriodicReader(logOutputExporter{w: log.Writer()})` + a `resource` (a fixed `service.name="sovereign-node"` + `service.instance.id=nodeIDHex`; a future fork attributes per-region — §6). The `telemetry.Init(meter)` call runs BEFORE `metrics.NewTelemetryBridge()` (so the bridge captures the post-`Init` SSoT slice — `telemetry.Counters()` at `NewTelemetryBridge` reads the snapshot `rebuildCounters` rebinds). The OTel reader exports through `logOutputExporter` (the operator log stream) — a SEPARATE destination from the bridge's `metricsExp.Registry()` → `/metrics` scrape. The bridge reads CUMULATIVE via `Value()`; the OTel callback reads DELTA via `lastReported`; cumulative == sum-of-deltas across the two; they never collide at `/metrics` because OTel is NOT a prometheus Collector. The `MeterProvider.Shutdown` is deferred on the graceful-exit path (the controller flushes the unreported-batch on Shutdown — §1.1).

**Gating:** `--otel=false` (the DEFAULT) keeps the Day-18 bridge-alone behavior byte-identical (the synchronous-nop Meter fallback in `registry.go` governs; the bridge still scrapes 12 cumulative series). `--otel=true` arms `Init`; `--otel-interval=60s` (the OTel SDK default) is the periodic reader cadence. The `PeriodicReader.Shutdown` path (the prompt §III honest-failure-mode named) is also `-race` clean.
