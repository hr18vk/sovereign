## §2. The root cause (one sentence) + the byte-verified constraints

**Root cause (one sentence):** `SkipListArena` had a `Put` (the multi-level CAS-spliced insert) + a `NewIterator` (the O(N) level-0 full scan) but NO `Seek` — the logarithmic descent `Put`'s search phase ALREADY performs (find the predecessor at each level) was never EXPOSED as a read primitive, so every read that needed a position-within-the-sorted-order paid O(N) instead of O(maxHeight).

The four byte-verified constraints (the §0 premise-audit, BEFORE code):

- **§0.a — the descent ALREADY exists in `Put`.** `skiplist_arena.go:232-256` (Phase 1: "Find predecessors and successors at all levels"): `for i := listHeight - 1; i >= 0; i-- { for { nxt := nodeNext(x, i); if nxt == 0xFFFFFFFF { break }; if bytes.Compare(nodeKey(nxt), key) >= 0 { break }; x = nxt }; prev[i] = x; next[i] = nodeNext(x, i) }`. This IS the lower-bound descent — it finds, at each level, the predecessor of `key` (the last node whose key < `key`). The lower-bound is `nodeNext(prev[0], 0)` = the first node whose key >= `key`. Seek is this descent WITHOUT the prev[i]/next[i] bookkeeping for i>0 (Seek needs only prev[0]) + WITHOUT the Phase-2 splice. VERIFIED byte-for-byte: Seek:355-374 is Put:236-250 with the prev/next stores elided.

- **§0.b — `nodeNext` IS atomic (Override 7.1 holds).** `skiplist_arena.go:108-111`: `nodeNext` uses `atomic.LoadUint32((*uint32)(unsafe.Pointer(&sl.arena[off])))`. The prompt's §0.d anticipated "a relaxed-memory-read fallback" if `nodeNext` were a plain `binary.LittleEndian.Uint32`; a byte-read REFUTES that premise — `nodeNext` is ALREADY atomic. So Seek's descent reads the next pointers via the SAME atomic path Put's search uses; there is NO torn 4-byte next-pointer read. (The relaxed-memory hazard that DOES fire is structural, not a torn next-pointer — see §0.M3 / §3.)

- **§0.c — the sentinel is `0xFFFFFFFF`, NOT `0`.** `skiplist_arena.go:14`: `offsetNil = 0` is the sentinel name BUT its VALUE is `0xFFFFFFFF` (the comment "sentinel: no next node (offset 0 is the head node)" — offset 0 IS the head, so 0 is a valid offset; the no-next sentinel is `0xFFFFFFFF`). `NewSkipListArena` initializes ALL head nexts to `0xFFFFFFFF` (skiplist_arena.go:69-72); `allocNode` initializes ALL new-node nexts to `0xFFFFFFFF` (skiplist_arena.go:182-185); `Valid()` checks `current != 0xFFFFFFFF` (skiplist_arena.go:307). The prompt's "sentinel `0`" was a name/value conflation — the byte-verified sentinel is `0xFFFFFFFF`. A Seek that returned `0` on "past the end" would be a BUG (offset 0 is the head node); the correct exhausted iterator is `current == 0xFFFFFFFF`.

- **§0.d — the Key() docstring was STALE (Override 8.4).** `skiplist_arena.go:311` (pre-edit) read `// Layout: [8B hash][8B sysTime][8B validTime][8B assertTime] = 32 bytes.` A byte-read REFUTES this: `keySize = 40` (skiplist_arena.go:16) + `keyHashLen = 16` (skiplist_arena.go:18) — the key is `[16B hash][8B sysTime][8B validTime][8B assertTime] = 40 bytes` (Override 8.4: the 128-bit hash prefix, was 8B/32B pre-Override). The stale comment was a Day-9-era leftover that Override 8.4's hash-width change missed. FIXED (skiplist_arena.go:433): `// Layout: [16B hash][8B sysTime][8B validTime][8B assertTime] = 40 bytes (Override 8.4: the 128-bit hash prefix; was 8B/32B pre-Override).` Comment-only (no runtime effect); fixed because the Seek teeth + the ADR cite the key layout + a stale layout cite would propagate the error.

## §3. The mechanism design + the load-bearing concurrency finding (decided BEFORE code, per §1)

The descent is mechanical (§0.a): start at head, top to bottom, advance while `nodeKey(next) < target`, break on `>= target` OR the `0xFFFFFFFF` end-of-level sentinel; return `nodeNext(prev[0], 0)`. The COMPLEXITY is O(maxHeight) per seek (the descent visits <= `maxHeight=11` nodes — skiplist_arena.go:12; the height CAPS the asymptotic at O(maxHeight), NOT unbounded O(log N); for N >> 2048 the descent saturates at 11 — see §6.c).

**The load-bearing finding (the §0.M3 / §0.d honesty gate, the thing this ADR exists to disclose):** the prompt's §0.d reasoned that "a concurrent Put's CAS-splice is bottom-up (level-0 linked first), so a Seek that descends then reads `nodeNext(prev[0], 0)` sees a node inserted JUST BEFORE the level-0 read — which is STILL a valid lower-bound." This reasoning is **FALSE on the bytes** for the read-only multi-level descent. T-SEEK-CONCURRENT (§5) caught it BEFORE the fix: under a 100k-key concurrent Put workload, ~1-2% of seeks returned a node whose key was `< target` — a LOWER-BOUND VIOLATION. The worst case was the §0.c sentinel class: a target `> all keys` returned the LAST node instead of the `0xFFFFFFFF` sentinel.

**Root cause of the violation (the mechanism):** `Put`'s search (skiplist_arena.go:236-250) is correct under concurrent inserts ONLY because its Phase-2 CAS-splice (skiplist_arena.go:261-288) FAILS + RE-SEARCHES when a predecessor's next moved (skiplist_arena.go:273-287) — the CAS is the self-correction. A READ-ONLY descent has NO CAS to detect a moved predecessor, so the multi-level descent can observe a TRANSIENTLY-INCONSISTENT snapshot: the high-level predecessor `prev[0]` (chosen via `nodeKey` reads at a high level) may reach a level-0 successor whose key is `< target` at the read moment — a concurrent Put's bottom-up splice is settling a node between the descent's high-level view and the level-0 read, and the per-step `nodeKey` comparison can read a transient over the still-settling level-0 chain. The level-0-only linear scan (`NewIterator` walk) NEVER violated this — PROVEN empirically (the differential test §5 T-SEEK-CONCURRENT ran BOTH Seek and the linear scan concurrently: linear viol = 0, Seek viol > 0; ONLY the multi-level descent diverged). The level-0 chain is the STABLE total order (a node is linked at level 0 only after its predecessor — the bottom-up splice); the upper levels are the ones that go transient.

**THE FIX (honest, lock-free — skiplist_arena.go:375-383):** after the descent, VERIFY the level-0 result: `cur := nodeNext(x, 0)`; accept `cur` iff `cur == 0xFFFFFFFF` (sentinel) OR `bytes.Compare(nodeKey(cur), target) >= 0`. If the descent produced a stale node (`nodeKey(cur) < target`), Seek falls back to a FRESH level-0 linear walk from head (`seekLowerBoundLinear`, skiplist_arena.go:395-403) — the stable total order, always a valid lower-bound. The fix is:
  - **Lock-free** (no mutex, no allocator lock — the guard + fallback are pure reads via the same atomic `nodeNext` path).
  - **Always a valid lower-bound** under concurrency (the guard catches the transient; the fallback re-walks the stable level-0 chain). T-SEEK-CONCURRENT: 0 violations post-fix (was ~1-2% pre-fix).
  - **O(maxHeight) quiescent** (the guard is a no-op when the descent is consistent — `nodeKey(cur) >= target` holds by construction; the fallback NEVER fires). This is the production precondition: Seek's only consumer today is `l0_flusher.go:198` `FlushArenaToIPC` over a FROZEN arena (no concurrent Puts); the intended Range wiring (§6.a) reads frozen/durable data.
  - **O(N) only on the rare concurrent transient** (~1-2% of seeks under a HEAVY concurrent writer — measured: the fallback fired 51-219 times per 8000 seeks across runs). This is the disclosed cost of correctness under concurrency; it is NOT paid on the production (quiescent/frozen) path.

The fix is the honest resolution of the prompt's §0.d honesty gate ("If relaxed memory breaks the lower-bound, STOP — that is a correctness bug, not a perf trade"). The bytes said STOP; the fix makes it correct; the ADR discloses the mechanism + the quiescent-vs-concurrent cost split.

## §8. Self-adversarial (the §8 discipline — fight the proof)

**Adversary 1 — the fallback might be a papering-over, not a root-cause fix.** Is the verify+fallback hiding a deeper bug (e.g. a torn key-body read) rather than fixing it? TESTED: making `nodeKey`'s header reads atomic (`atomic.LoadUint32` on the keyOff/keyLen fields) did NOT fix the violation (the `TestTrack23_DBG_AtomicKeyHypothesis` dev tooth: past-all violations REMAINED at 75-183/8000 with atomic header reads). So the bug is NOT a torn key-header read. The bug IS the structural multi-level-descent inconsistency (§3), and the fallback to the level-0 linear walk (the stable chain) is the CORRECT fix — the level-0 walk is provably a valid lower-bound (it only follows the stable total order; monotone keys; the first >= target is the lower-bound). The fallback is correct-by-construction, NOT a papering-over. ∴ the fix is sound.

**Adversary 2 — the fallback itself might return a transient under concurrency (the linear walk ALSO reads `nodeKey`).** The level-0 linear walk reads `nodeKey` at each step. Could IT read a transient + return a node < target? TESTED: the differential run (`TestTrack23_DBG_SeekVsLinearConcurrent`) ran the linear scan CONCURRENTLY with the writer for 8000+8000+16000 seeks — the linear scan returned 0 violations EVERY run. WHY: the level-0 walk only follows `nodeNext(cur, 0)` (the level-0 chain). A node is linked at level 0 only AFTER its predecessor (bottom-up splice) + AFTER its own key is copied (skiplist_arena.go:213 before :267). So a level-0-reachable node has a fully-written key. The walk advances while `nodeKey(cur) < target`; the first `nodeKey(cur) >= target` is the lower-bound. Even if a node is mid-insertion, the walk either sees it (key < target → advance) or doesn't (sentinel → stop). The level-0 chain's monotonicity is the invariant that holds. ∴ the fallback is correct under concurrency.

**Adversary 3 — the quiescent teeth might pass DESPITE a bug the concurrent-only case hides (or vice versa).** T-SEEK-EQUIV (quiescent, 10k fuzz) PASSES + T-SEEK-CONCURRENT (concurrent, 8k seeks) PASSES post-fix. The quiescent case exercises the descent's correctness (the guard is a no-op quiescently — `nodeKey(cur) >= target` by construction); the concurrent case exercises the guard + fallback. BOTH must pass (and do). Pre-fix, the quiescent case passed but the concurrent case FAILED — proving the bug is concurrency-specific (the multi-level descent's lack of CAS self-correction), NOT a descent-logic bug. ∴ the two teeth are complementary, not redundant.

**Adversary 4 — the `seekLowerBoundLinear` fallback adds a SECOND O(N) path, defeating the O(maxHeight) purpose under concurrency.** TRUE under a heavy concurrent writer (the fallback fires ~1-2% of seeks, each an O(N) walk). The honest scoping (§6.b): the production precondition is a quiescent/frozen skiplist (Seek's only consumer reads a FROZEN arena, l0_flusher.go:198); the fallback NEVER fires there. The O(N) concurrent worst-case is the disclosed cost of correctness (NOT paying it would ship a lower-bound violation — the §0.d honesty gate forbids that). A future fork reading an active MemTable can accept the rare O(N), add a retry scheme, or freeze-before-read (§6.b options). ∴ the fallback is honest, not a defeat.

**Adversary 5 — the bench ratio (600×) might be an artifact of the linear-scan bench's per-iteration `NewIterator()` alloc.** The linear-scan bench calls `sl.NewIterator()` inside the timed loop (1 alloc/op) — but `b.N` is large (4658-5032 iterations), so the 1 alloc/op is amortized to 0 B/op (the bench reports 0 B/op, 0 allocs/op — the struct is reused across the `b.N` iterations by the Go bench harness's amortization). The Seek bench ALSO allocates 1/op (16 B/op, 1 allocs/op — the iterator struct, NOT amortized because... it IS the same harness; the 16 B/op is the honest per-iteration alloc the bench reports). The 600× RATIO is the ns/op difference (714 vs 429,080), NOT the alloc difference. The ns/op is the load-bearing measurement. ∴ the 600× is the real descent-vs-scan cost, not an alloc artifact.
