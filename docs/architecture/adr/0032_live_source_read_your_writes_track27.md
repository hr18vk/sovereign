## §1. Context (the named gap; the Day-26 default-interval behavior OPENED it)

The engine's read path (`Resolver.AsOf`, `query.go:381`; `Resolver.Range`, `query.go:730`) is durable-ONLY: it lists L1 + L0 Arrow keys, downloads, scans, applies Filter2 (`sysTime <= txTime`) + Filter3 (the validTime window) + dominance (max `SystemTime` wins), and returns the dominant. The write path (`engine.InsertLocal`, `crdt.go:983`) CAS-spins the LIVE δ-CRDT HAMT's per-shard root — the entry is in the live HAMT IMMEDIATELY. The bridge (`pkg/durability/bridge.go:213`) periodically calls `AppendCheckpoint` → `SnapshotToLSM` (`snapshot.go:391`) which READS `engine.State().ForEach` + writes the L0 Arrow index. The two paths are joined ONLY at the checkpoint boundary.

The gap: between an insert and the next checkpoint, the live HAMT holds the entry but the durable tier does NOT → `/v1/query` 404s on a row the node JUST accepted. This is NOT a data-loss bug (the entry IS durable in the WAL, `pkg/durability` fsync-per-mutation) — it is a READ-VISIBILITY gap: the read path consults a STALE projection of the live state. With the DEFAULT checkpoint interval (1000 mutations) the gap is the COMMON case, not the edge — Day-26's harness REQUIRED `--wal-checkpoint-interval=1` to make the durable read path work AT ALL, which is the load-bearing empirical proof the gap is real. A world-#1 engine does not 404 a row it just wrote.

## §2. The root cause (one sentence) + the byte-verified constraints (the §0 premise-audit, MEASURED before code)
