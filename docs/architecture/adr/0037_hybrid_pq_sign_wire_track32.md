## §1 — The Decision

WIRE the SIGN half of the hybrid post-quantum moat (the Day-31 ADR-0036 wired the VERIFY half — the BOTH-required gate — + disclosed the honest NOT-YET: under `--hybrid-verify` EVERY v1 frame is REJECTED because the v1 wire carries ONE Ed25519 sig + the Directory carries ONE `ed25519.PublicKey`). Day 32 closes that NOT-YET: `ShipBatchHybrid` signs the marshaled `CRDTDeltaBatch` wire under BOTH Ed25519 + ML-DSA-65 over the SAME 120-byte SHAKE256 pad (the M1 amortized pad — ONE PQ sign per BATCH, NOT per delta), the `HybridEnvelope` frame carries BOTH sigs, the identity Directory is provisioned with BOTH pubkeys (`RegisterPQ` + `LookupBoth`), the `DispatchFrame` 4-way router routes the hybrid magic to `HandleHybridFrame`, `VerifyBatchHybrid` is the BOTH-required batch verify gate, + the `HybridFrameAccepted` counter is the 23rd SSoT (the operator-VISIBLE proof the moat is in USE, not just wired). The fork is OPT-IN (the Day-19/23/29/30/31 opt-IN precedent): the `--hybrid-sign` flag (default false) keeps the self-originated delta path on the v1 `BatchEnvelope` — byte-identical Day-31 (NO hybrid frame is produced or accepted; the counter stays 0); the `--hybrid-verify` flag (Day-31, default false) keeps the receive path on the classical `VerifyCRDTFrame` seam. NONE of the 5 FROZEN files are touched (the Day-29 `44f89527` streak is PRESERVED — NO streak-breaker this fork; the hybrid-SIGN layer is a mesh/identity/attribution addition, NOT a CRDT/data-layer change).

**THE M1 SHAKE256-PAD AMORTIZATION (the load-bearing mechanism).** The hybrid sign does NOT sign `batchWire` twice (the 64-byte Ed25519 + the 3309-byte ML-DSA-65 over the raw capnp wire would DOUBLE the per-batch sign cost + triple the wire). Instead `SignCRDTFrame_Hybrid` derives a FIXED 120-byte SHAKE256 pad of `batchWire` (the `HashBatchWireToFrame120` helper — the SAME 120-byte frame the `pq_preview` `SignCRDTFrame_PostQuantum` already used), then signs the PAD under BOTH keys: `ed25519.Sign(edPriv, pad120)` + `mldsa65.Sign(pqPriv, pad120)`. The verify re-derives the pad + checks BOTH sigs over it. The amortization is the point: ONE PQ sign per BATCH of N deltas (the `--batch-size` knob, default `DefaultBatchSize`), NOT one PQ sign per delta. A per-frame hybrid would sign the 120-byte pad of a ONE-delta "batch" per frame (NO amortization — the 73.7µs PQ sign per delta, NOT per batch); the BATCH is the load-bearing shape, so `--hybrid-sign` FORCES the `shipBatchedDelta` path even when `--batch-size <= 1` (the §4 wiring detail the teeth caught — see §6).

**THE M3 BOTH-GATE (defense-in-depth, carried from Day-31).** `VerifyBatchHybrid` checks BOTH the Ed25519 sig AND the ML-DSA-65 sig over the SAME pad; EITHER failure rejects the frame. The BOTH gate (return `edOK && pqOK`) is the load-bearing choice — the EITHER-or gate (return `pqOK || edOK`) is the defense-in-depth INVERSION: a classical break (a future Ed25519 fault) would compromise a PQ frame under EITHER-or (the PQ sig still verifies, so the frame accepts), but under BOTH the classical break rejects. The `T-PQ-HYBRID-EITHER-OR-CONTROL` BUG-INJECT tooth (Day-31) PROVES the BOTH gate is load-bearing; Day 32 carries the SAME gate to the batch verify (`VerifyBatchHybrid`).

**THE STRICT-MODE SYMMETRY (the M5 orthogonality).** The hybrid moat is STRICT in BOTH directions:
- a hybrid verifier (`--hybrid-verify=ON`) NEVER accepts a classical-only v1 frame (the v1 wire carries ONE Ed25519 sig; the BOTH gate rejects — `T-PQ-HYBRID-VERIFY-REJECTS-V1`)
- a non-hybrid verifier (`--hybrid-verify=OFF`) NEVER accepts a BOTH-sig hybrid frame (it cannot fall back to the classical single-sig verify on a BOTH-sig frame — `T-PQ-HYBRID-SIGN-VERIFY-OFF`)
The symmetry is the orthogonality the M5 names: the two flags are INDEPENDENT (sign + verify), + each side rejects the cross-class frame. A hybrid frame is ONLY accepted when BOTH `--hybrid-sign` (send) + `--hybrid-verify` (receive) are armed — the moat-in-USE posture.

**THE HONEST NOT-YET (the load-bearing scope disclosure).** The OOB peer-pubkey provisioning is a FUTURE fork — Day 32 assumes a STATICALLY-provisioned Directory (the harness registers the peer's PQ pubkey via `RegisterPQ` at construction; the production node registers its OWN PQ pubkey via `RegisterPQ` at boot — but does NOT yet gossip peer pubkeys). A node whose Directory does NOT carry a peer's ML-DSA-65 pubkey gets a `nil pqPub` from `LookupBoth` → the hybrid verify rejects (the STRICT mode). The directory-gossip fork (the peer-pubkey propagation) is the NEXT PQ fork. The cmd's mesh peer-dial loop is the Day-2 stub ("dial loop pending Day 2" in the node log) — a pre-existing codebase gap, NOT a Day-32 defect; the 2-node BINARY mesh cannot converge until that lands, so the runtime /verify is single-node (PRESENCE of the 23rd counter) + the E2E USEFUL proof (the counter FIRES >=1) is the in-process `day32Harness` (6/6 teeth GREEN).
