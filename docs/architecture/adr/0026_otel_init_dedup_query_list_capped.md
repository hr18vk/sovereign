# ADR-0026: Arm `telemetry.Init` at boot — dedup `QueryL0ListCapped` in `init()`, fill `rebuildCounters()`

**Status:** Accepted
**Date:** 2026-08-08
**Author:** Harsh Rawat
**Builds on:** ADR-0023 (the prometheus bridge, whose §6 named, as deferred work, the exact two landmines this change closes — the `QueryL0ListCapped` `init()` double and the `rebuildCounters()` omission — and whose two-exporter separation this change refreshes), ADR-0020 §6a (the `T_gc` auto-inference work this change unblocks by making the telemetry honest under a real Meter — still not implemented), ADR-0025 (the verify-assumptions-against-bytes discipline re-applied here: one plan assumption was corrected against the actual `go.mod` before shipping).

---

## §0. Root cause + the assumption-check findings

**§0.a ROOT CAUSE:** `telemetry.Init(realMeter)` calls `rebuildCounters(m)`, which reassigns the package-level `*Counter` vars from a fresh Meter — but `rebuildCounters()` constructed `QueryL0ListCapped` ZERO times (the omission, byte-verified: 0 assignment sites), so an `Init` call reassigns `QueryL0ListCapped` to nil and the use-site guard `internal/database/query.go:253` `if telemetry.QueryL0ListCapped != nil { ... Add(1) }` stops counting the cap-hit disclosure counter. Separately, `init()` built `QueryL0ListCapped` TWICE (the orphaned first object) — a latent double that was harmless under the existing bridge (which reads the distinct package VAR, not the invocation count) but had to be deduped before `Init` was armed, or the dedup discipline inside the same function would be hypocritical.

**§0.b Assumption-check finding #1: "zero new module deps" was false as assumed.** My plan assumed `go.mod` already carried everything needed: `go.opentelemetry.io/otel` v1.43.0 and `go.opentelemetry.io/otel/metric` v1.43.0 in the require block, `go.opentelemetry.io/otel/sdk` v1.43.0 + `go.opentelemetry.io/otel/sdk/metric` v1.43.0 resolved in `go.sum` — "do not touch go.mod or go.sum unless a `go build ./...` proves a missing dep." The byte-verified finding: `go.mod`'s direct `require` block carried ONLY `go.opentelemetry.io/otel/metric` (the `metric.Meter` interface the registry uses) plus `go.opentelemetry.io/otel` (indirect). `otel/sdk` + `otel/sdk/metric` were in `go.sum` (transitive, via the metric package) but NOT in the `go.mod` direct `require` block. `cmd/sovereign-node/otel.go` imports `sdkmetric "go.opentelemetry.io/otel/sdk/metric"`, `"go.opentelemetry.io/otel/sdk/resource"`, and `"go.opentelemetry.io/otel/attribute"` (for `resource.NewWithAttributes` + `attribute.String("service.name", ...)`), so `go build ./cmd/sovereign-node/` (default `-mod=readonly`) emitted `go: updates to go.mod needed`. The fix: `go mod tidy` promoted `otel/sdk` + `otel/sdk/metric` from indirect to direct requires and added the transitive `go-logr/logr` + `go-logr/stdr` + `go.opentelemetry.io/auto/sdk` + `otel/trace` indirects. NO new module version was added (all already in `go.sum` at v1.43.0); the deps were already resolved — the go.mod direct-require list was simply stale. The plan said "do not touch go.mod"; the bytes said go.mod had to be tidied to admit the direct imports the new production code makes. Disclosed here, not shipped as a build-broken tree.

**§0.c Assumption-check finding #2 (the schema-URL landmine):** the first T-OTEL-EXPORT guard run FAILED with `resource.Merge: conflicting Schema URL: https://opentelemetry.io/schemas/1.40.0 and https://opentelemetry.io/schemas/1.4.0`. `resource.Default()` (the SDK builtin) uses `semconv.SchemaURL` = `"https://opentelemetry.io/schemas/1.40.0"` (the semconv v1.40.0 const); my first-draft code used `"https://opentelemetry.io/schemas/1.4.0"` (a stale, v1.4.0-era schema URL). `resource.Merge` returns `ErrSchemaURLConflict` on mismatched non-empty schema URLs. The fix: use `"https://opentelemetry.io/schemas/1.40.0"` (the version the SDK's own `Default()` builtin uses) in both `cmd/sovereign-node/otel.go` and the test guard. The `semconv` package is NOT a direct `go.mod` dep (using the string literal avoids adding it); a future change may import `go.opentelemetry.io/otel/semconv/v1.40.0` for the `ServiceName` const (§6 — deliberate anti-scope-creep: do not auto-infer the OTel resource; use a fixed service.name).

**§0.d The double-count trap ADR-0023 pre-traced is disarmed by the two-exporter separation, refreshed here.** The bridge reads CUMULATIVE via `Counter.Value()` (telemetry.go:223) and never touches `lastReported`. The OTel callback (`registerInt64Counter`, telemetry.go:~283) reads DELTA via `lastReported` (the per-interval delta the OTel exporter expects). Both layers read the SAME underlying `*Counter` objects — the bridge cumulative, OTel delta — WITHOUT double-counting at `/metrics` because the OTel reader is a `logOutputExporter` (a `sdkmetric.Exporter` writing to `log.Writer()`) driven by a `PeriodicReader`, NOT a `prometheus.Collector` registered with the bridge's `metricsExp.Registry()`. The two export through DIFFERENT destinations. Wiring the OTel reader onto the bridge's prometheus Registry WOULD double-count — refused (the T-OTEL-EXPORT guard asserts the OTel reader is a `ManualReader`, a separate destination; the T-ARMED guard asserts the bridge does NOT call `Init`). An OTel-otlp-to-prometheus bridge is a different change (§6).

**§0.e CONSTRAINT — the "Init uncalled" contract flip.** The earlier contract "telemetry.Init has ZERO production callers" existed only as PROSE (a comment in `telemetry_bridge_test.go:398`), not a gated assertion — no test asserted it and there was no grep for `Init` callers. I deliberately flip this contract: arming `Init` is the deliverable. The new gated guard is `TestArmedBridge` (`pkg/metrics/telemetry_init_armed_test.go`): a grep asserting `telemetry.Init` has EXACTLY ONE production caller (under `cmd/sovereign-node/` — the `armOTel` helper in `otel.go`), and that the bridge (`pkg/metrics`) does NOT call it. The old Init-uncalled prose is refreshed in the bridge test comment to point at T-ARMED — a deliberate, disclosed contract flip, not a silent deletion (§7).

## §1. Context

The engine's observability has two layers, designed in ADR-0023 to be independent:

1. **The prometheus bridge** (`pkg/metrics/telemetry_bridge.go`) — a `prometheus.Collector` reading the 12 distinct `internal/telemetry` `*Counter` objects CUMULATIVELY via `Counter.Value()`, registered into the per-process `metricsExp.Registry()`, scraped via `/metrics`. In production since ADR-0023.
2. **The OTel layer** (`internal/telemetry` registry + the `Int64ObservableCounter` callbacks) — reads each counter DELTA via `lastReported` on the collector's cadence. A documented no-op until now: `telemetry.Init` had zero production callers, so the package-level Meter stayed nil (the synchronous-nop default) and no observable was ever registered.

ADR-0023 §6.2 named two landmines on the OTel layer, disclosed as deferred work explicitly left for "the future work that arms Init":

- `init()` builds `QueryL0ListCapped` twice (the orphaned first object);
- `rebuildCounters()` builds `QueryL0ListCapped` zero times — so an `Init(realMeter)` call would reassign the var to nil, and the use-site guard `query.go:253` would silently stop counting the cap-hit disclosure counter.

This change is that work. It (a) dedups the `init()` construction (2 → 1), (b) fills `rebuildCounters()` (0 → 1), (c) arms `telemetry.Init(realMeter)` at boot in `cmd/sovereign-node` with a real `go.opentelemetry.io/otel/sdk/metric` `MeterProvider` (deps in `go.sum` v1.43.0; `go.mod` tidied to promote indirects — §0.b), gated `--otel` (a node running with OTel off keeps the bridge-alone behavior), and (d) unblocks the `T_gc` auto-inference work (ADR-0020 §6a) — not implemented; `T_gc` remains administrator-set.

## §2. The contract guards (RED → GREEN)

All six new guards are gated and green. The Init-driving guards (T-DEDUP-FILL, T-OMISSION-FIRED, T-OTEL-EXPORT) run in a fresh subprocess — re-invoking the test binary with a sentinel env var — because `Init`'s once-per-process guard (`registry.go:42` — a second `Init` in-process is rejected and logged) makes a single in-process test unable to drive `Init` after the first. §7 explains the subprocess-vs-singleton choice.

- **T-DEDUP-INIT** (`internal/telemetry/otel_init_test.go`, `TestQueryL0ListCappedConstructedOnce`): a source-parse guard counting `QueryL0ListCapped = newCounter(m,` construction sites. The whole-file count is 2 (one in `init`, one in `rebuildCounters` — consistent with the 11 siblings that also appear in both sites); the `init()` count alone is 1 (the dedup 2 → 1). It refuses a refactor that hides the construction behind a helper: the count is at the construction site (the DRY-rejection, §3).

- **T-DEDUP-FILL** (`TestDedupFill_Subproc`, load-bearing): the subprocess re-invokes the test binary with the sentinel env var set; the entry constructs a real `sdkmetric.ManualReader` + `MeterProvider`, calls `telemetry.Init(meter)` ONCE, and asserts `QueryL0ListCapped != nil` post-Init. The RED: a stale tree where `rebuildCounters` omitted the fill would leave `QueryL0ListCapped` nil post-Init. This proves the fill is load-bearing at the construction site.

- **T-UNCHANGED** (`TestCountersDistinctAfterDedup`, regression guard): `Counters()` still carries exactly 12 DISTINCT counters with 0 duplicate names. The dedup is at the construction site, not the var-slice, so the bridge's 12-series property survives (`TestTelemetryCounterEnumeration` stays green without a bridge edit).

- **T-OMISSION-FIRED** (`TestOmissionFired_Subproc`, the headline guard): the subprocess `Init`s the Meter, drives `QueryL0ListCapped.Add(1)` twice, and asserts the counter ADVANCES. The RED: the omission would leave `QueryL0ListCapped` nil and the use-site guard would skip `Add`. This proves the omission is closed at the USE site, not just the construction site.

- **T-OTEL-EXPORT** (`TestOtelExport_Subproc`, the arm-end guard): the subprocess `Init`s a real `MeterProvider` with a `ManualReader` (a separate destination from the bridge's prometheus Registry), Inc's a counter 7 times, `Collect`s, and asserts the observed OTel value EQUALS the cumulative `Counter.Value()` (cumulative == sum-of-deltas) AND that `lastReported` ADVANCED (the OTel callback fired). The RED hazard: wiring the OTel reader onto the bridge's prometheus Registry would double-count — refused (the reader is a `ManualReader`, not a prometheus Collector).

- **T-ARMED** (`pkg/metrics/telemetry_init_armed_test.go`, `TestArmedBridge`, gated, cross-package): a source-grep over `internal/`, `pkg/`, `cmd/` asserts `telemetry.Init(` has EXACTLY ONE production caller (under `cmd/sovereign-node/` — the `armOTel` helper in `otel.go`) and that the bridge (`pkg/metrics`) does NOT call it (the two-exporter separation). This flips the old prose "Init has ZERO production callers" into a gated contract.

A 7th guard, **T-LASTREPORTED** (`TestLastReportedObservableUnderInit`, subprocess), documents the §6 finding that arming `Init` makes `lastReported` OBSERVABLE under OTel (it was 0 before, because `Init` was uncalled); the bridge's `TestLastReportedUntouchedByBridge` invariant (the bridge never touches `lastReported`) is unaffected — the guard runs in a subprocess so it does not contaminate the in-process baseline.

The race gate confirmed: the OTel arm is a background `PeriodicReader` goroutine; a data-plane `Inc` concurrent with the callback's `lastReported.Store` under `-race` is NOT a race (the `Counter` is a LongAdder — dispersion; `lastReported` is an `atomic.Uint64` — the CAS is the consultation; `-race` clean across `internal/telemetry` + `pkg/metrics`).

## §3. The dedup mechanism + the two-exporter separation (decided before code)

**The dedup:** in `init()`, DELETE one of the two `QueryL0ListCapped = newCounter(m, ...)` blocks (they were byte-identical — delete one, keep a single block). In `rebuildCounters()`, ADD the same single construction at the analogous position (after `MemTableFlushTotal`, before `OffHeapAllocatedBytes` — matching `init()`'s order so the registered-instrument order under the OTel Meter is stable across the two construction sites; a drift in order is a registered-instrument-order drift observable to a collector). The construction is now consistent with its 11 siblings (each is built in BOTH `init` + `rebuildCounters`); `QueryL0ListCapped` was the lone exception, now the 12th-in-both. The `allCounters()` registry slice is unchanged (it reads the package VAR; the dedup is at the construction site, so the 12-distinct-counters property is preserved by construction — the bridge's series-count guard stays green without a bridge edit). I considered and rejected a shared-constructor DRY refactor: a single shared constructor would be a refactor, and minimal blast radius is two literal constructions — the same pattern the other 11 counters already use.

**The two-exporter separation (§0.d refreshed):** `armOTel` (`cmd/sovereign-node/otel.go`) constructs a `sdkmetric.NewMeterProvider` with a `sdkmetric.NewPeriodicReader(logOutputExporter{w: log.Writer()})` and a `resource` (a fixed `service.name="sovereign-node"` + `service.instance.id=nodeIDHex`; a future change attributes per-region — §6). The `telemetry.Init(meter)` call runs BEFORE `metrics.NewTelemetryBridge()`, so the bridge captures the post-`Init` registry slice — `telemetry.Counters()` at `NewTelemetryBridge` reads the snapshot `rebuildCounters` rebinds. The OTel reader exports through `logOutputExporter` (the node's log stream) — a separate destination from the bridge's `metricsExp.Registry()` → `/metrics` scrape. The bridge reads CUMULATIVE via `Value()`; the OTel callback reads DELTA via `lastReported`; cumulative == sum-of-deltas across the two; they never collide at `/metrics` because OTel is not a prometheus Collector. The `MeterProvider.Shutdown` is deferred on the graceful-exit path (the controller flushes the unreported batch on Shutdown).

**Gating:** `--otel=false` (the default) keeps the bridge-alone behavior byte-identical (the synchronous-nop Meter fallback in `registry.go` governs; the bridge still scrapes 12 cumulative series). `--otel=true` arms `Init`; `--otel-interval=60s` (the OTel SDK default) is the periodic-reader cadence. Honest-disabled, not a silent no-op: the arm-off path loud-logs "OTel OFF — prometheus bridge serves /metrics alone".

## §4. The byte chain

- `registry.go init()`: 2 `QueryL0ListCapped = newCounter(m,` sites → 1 (the dedup). The orphaned first object is gone.
- `registry.go rebuildCounters()`: 0 → 1 `QueryL0ListCapped = newCounter(m,` site at the same position (after `MemTableFlushTotal`, before `OffHeapAllocatedBytes`).
- `Counters()` registry slice: unchanged — still exactly 12 distinct, 0 dups (T-UNCHANGED + the bridge's `TestTelemetryCounterEnumeration` stay green).
- The `newCounter` invocation count: `init()` was 13 invocations including the `QueryL0ListCapped` double → now 12 (the dedup); `rebuildCounters()` was 11 (the omission) → now 12 (the fill). So 24 → 24 (the double in init −1 = 12; the fill in rebuildCounters +1 = 12; 12 + 12 = 24 — unchanged invocation count; the distinct vars stay 12). My original plan predicted "invocation count: 13 → 12 (init) and 0 → 1 (rebuildCounters) → the newCounter-invoke total drops by 1 net"; the byte-verified math: `init()` was 13 (12 distinct + 1 dup) → 12 (net −1); `rebuildCounters()` was 11 (0 QueryL0ListCapped) → 12 (+1); total 24 → 24 (net 0, NOT −1 — the plan's "drops by 1 net" double-counted: −1 init dedup + +1 rebuild fill = 0 net). Disclosed in §7 (the M1 correction).
- `cmd/sovereign-node/main.go`: `armOTel(cfg.otelEnabled, hex.EncodeToString(nodeID[:]), cfg.otelInterval)` BEFORE `metrics.NewTelemetryBridge()`; `defer otelShutdown(context.Background())` on the graceful-exit path.
- `cmd/sovereign-node/otel.go` (new): `armOTel` + `logOutputExporter` (the `sdkmetric.Exporter` writing to `log.Writer()`; DeltaTemporality for counters, Cumulative for gauges).
- `go.mod`/`go.sum`: `otel/sdk` + `otel/sdk/metric` promoted indirect → direct (§0.b; no new versions); `go-logr/logr` + `go-logr/stdr` + `go.opentelemetry.io/auto/sdk` + `otel/trace` added as transitive indirects.
- The five core files: unchanged (no core file touched).

## §5. The honest headline

The deliverable is operational observability: `telemetry.Init` is armed at boot with a real `go.opentelemetry.io/otel/sdk/metric` `MeterProvider` (gated `--otel`; deps in `go.sum` v1.43.0; `go.mod` tidied to promote indirects — §0.b), the `QueryL0ListCapped` construction-duplicate in `init()` and the omission in `rebuildCounters()` are closed (dedup 2→1 in init, fill 0→1 in rebuildCounters), and the cap-hit disclosure counter stays non-nil under `Init` (the use-site guard at `query.go:253` keeps counting). The bridge's 12 prometheus series are unchanged (the two-exporter separation — prometheus and OTel export through different destinations; not a double-count). The `T_gc` auto-inference work (ADR-0020 §6a) is unblocked but not implemented. There is no alloc headline to claim; the OTel callback firing makes `lastReported` observable (it was 0 before, because `Init` was uncalled) — §6.

## §6. Honest open items and residuals

1. **`lastReported` is now observable under a real Meter.** Before this change, `lastReported` stayed 0 across all tests (the synchronous-nop default) — the existing `TestLastReportedUntouchedByBridge` guard asserted `lastReported == 0` as the bridge-doesn't-touch-it invariant. Arming `Init` makes the OTel callback fire (on the periodic reader's cadence), advancing `lastReported` — so `lastReported == 0` is no longer a universal baseline. The bridge invariant is unaffected: it asserted the field-level property (the bridge never reads/writes `lastReported`), not a universal value. The T-LASTREPORTED guard (subprocess) documents this; the in-process `TestLastReportedUntouchedByBridge` stays green because it runs before any `Init` in its test process. A future change that binds a test-Meter in the same process as that guard must account for this ("arming Init makes lastReported observable under OTel; the bridge invariant is unaffected").

2. **The scrape path is not zero-alloc (ADR-0023 §6.3 residual, unchanged).** The existing alloc measurement is 62 allocs/Collect (12 bridge-read `Value()` + 50 prometheus const-metric constructors); this change does not touch the bridge, so the residual is unchanged. The OTel `logOutputExporter.Export` path is a separate allocation (a `fmt.Fprintf` per batch — off the data plane, on the periodic reader's cadence); not pooled. A future change could pool the dto/observation (disclosed, not this change).

3. **The `service.name` resource is fixed (not per-region).** `armOTel` uses `attribute.String("service.name", "sovereign-node")` + `service.instance.id=nodeIDHex`. A future change attributes per-region (the anti-scope-creep rule: do not auto-infer the OTel resource — this change uses a fixed name derived from the nodeID). The `semconv` package is not a direct dep (the schema URL is a string literal); a future change may import `go.opentelemetry.io/otel/semconv/v1.40.0` for the `ServiceName` const.

4. **The `T_gc` auto-inference work (ADR-0020 §6a) is unblocked, not implemented.** This change makes the telemetry honest under a real Meter (the prerequisite); `T_gc` remains an explicitly administrator-set retention policy (the standing contract: never auto-prune). The inference is follow-up work.

5. **The OTel-otlp-to-prometheus bridge is a different change.** Today the OTel reader is a `logOutputExporter` (the node's log stream); the bridge is the prometheus `/metrics` scrape. Wiring OTel-otlp into the bridge's Registry would double-count — refused (§0.d). An OTel-collector→prometheus pipeline is a future operations track. The two-exporter separation is the load-bearing invariant.

6. **`TestJemallocAllocator_Reallocate` is a pre-existing cgo flake** (recorded in ADR-0020) under heavy-memtable-test memory pressure — not a regression from this change, which touches `internal/telemetry` + `cmd` + `pkg/metrics`, not the allocator.

## §8. What this change does NOT close

1. **Did the OTel callback introduce a data race on `lastReported` under `-race`?** The data-plane `Inc` is on the LongAdder (dispersion — one stripe per P, no cross-core coherence); `lastReported` is an `atomic.Uint64` CAS'd inside the callback (`registerInt64Counter`'s `lastReported.CompareAndSwap(prev, now)`). The `-race` gate ran the full `internal/telemetry` + `pkg/metrics` packages green — the callback touching `lastReported` concurrently with a data-plane `Inc` is not a race (the two touch different fields — `stripes[*].value` vs `lastReported`; the CAS is the consultation). The `PeriodicReader.Shutdown` path is also `-race` clean. Closed for this scope; a production load with a real OTLP exporter under sustained `-race` is a future gate.

2. **Did the dedup leak a duplicate name into the registry slice?** No — `Counters()` carries 12 distinct, 0 dups (T-UNCHANGED + the bridge's `TestTelemetryCounterEnumeration`). The dedup is at the construction site; the `allCounters()` slice reads the package VAR, not the invocation count. Closed.

3. **Did arming `Init` contaminate the in-process `lastReported` baseline?** No — the Init-driving guards (T-DEDUP-FILL, T-OMISSION-FIRED, T-OTEL-EXPORT, T-LASTREPORTED) run in a subprocess; the in-process `TestLastReportedUntouchedByBridge` runs in its own test process and asserts `lastReported == 0` before any `Init` in that process. The `-race` gate ran both in the same binary with no contamination (the subprocess's `Init` does not re-enter the parent's once-guard). Closed; the subprocess choice is documented in §7.

4. **Did the OTel reader share a Registry with the bridge?** No — `armOTel` uses a `PeriodicReader` over `logOutputExporter` (a `sdkmetric.Exporter`); the bridge uses `metricsExp.Registry().MustRegister(telemetryBridge)`. The two are separate objects; the T-OTEL-EXPORT guard's reader is a `ManualReader`, and T-ARMED asserts the bridge does not call `Init`. Closed (the §0.d trap).
