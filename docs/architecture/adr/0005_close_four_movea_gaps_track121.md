**Decision (SCOPED, post-Move-A2):** Track 12.1 landed the CODE for all four closers and CLOSED Gaps 1+4 on silicon (the epoll ingress loop + the receiver.go wiring — mechanically verified: `pkg/receive/ingress_epoll.go` is gated `ebpf_kernel`, drives EPOLLIN|EPOLLET over the 32 fds, reassembles length-prefixed frames, invokes `Receiver.HandleFrame`; `receiver.go` md5 re-lock `095188cd...→9dfde188...` is a doc-comment only, default build byte-identical; FROZEN substrate md5 unchanged). But Gaps 2+3 are NOT proven on silicon this track (the bench sends to 127.0.0.1, not a real NIC; the t.Fatalf NEGATIVE tooth is PRESENT in prose but ABSENT from the code; no `.log` artifact was committed):

- **Gap 1 + Gap 4 (epoll loop + wiring):** `pkg/receive/ingress_epoll.go` (gated `ebpf_kernel`) implements `EpollIngress` — an edge-triggered epoll loop over the 32 SO_REUSEPORT fds from the 12.0 `KernelFanout`. It EpollCtl-ADDs the 32 fds (EPOLLIN|EPOLLET), EpollWait-drives them, Recvfrom's each ready fd, reassembles length-prefixed frames (the GAP-2 wire shape `[uint32 frameLen BE][envelope bytes]` from `forward.go:104 LengthPrefixFrame`), and invokes `Receiver.HandleFrame` on each frame. The wiring is ABOVE HandleFrame (delivery), NOT inside it — the gate-stack order at `receiver.go:244` (cheap gates → Verify) is PROVEN and untouched. The DEFAULT build (no tag) EXCLUDES `ingress_epoll.go` entirely — `HandleFrame` is byte-identical to HEAD. Under `-tags ebpf_kernel` the loop is the SILICON form of the §2.X1(a) contract: epoll (this loop) COUPLED WITH SO_ATTACH_REUSEPORT_EBPF (the 12.0 attach the caller already did). The epoll precedent is the EXISTING live loop `internal/transport/capnp_server.go:119/222/486` — CITED, not duplicated.

- **Gap 2 (real NIC) — NOT CLOSED this track (pending 12.2):** `TestEBPFEpollIngress_RealNIC` is WRITTEN to bind the SO_REUSEPORT group to a non-127.0.0.1 interface (secondary ENI private IP 172.31.5.252, or a tc-redirect target), It records the interface name, `ethtool -l` channel counts, and `nproc` in the .log header. It asserts the 12.0 stickiness gate (0/N mis-routes across a 4-tuple roam) on the real interface. A flow "pinned to a core" now pins to a MAILBOX that has hardware delivery, so the "concurrent scale" / "cache invalidation" claim of Phase3.md:102 is measurable.

- **Gap 3 (perf bench) — NOT CLOSED this track (pending 12.2):** `BenchmarkEBPFDelivery_vs_HashFallback_32c` EXISTS and drives a churn workload, BUT (DEFECT-1) it does NOT contain the `t.Fatalf` honest-NEGATIVE tooth the prompt required — it runs col A and col B as two `b.Run` sub-benches and never COMPARES them; and (DEFECT-3) it sends to `127.0.0.1` (loopback), NOT the real NIC Gap 2 was about. The prompt said (vary the CID at high rate so the SOCKHASH lookup exercises cache-miss as well as hit). Two columns:
  - col A — eBPF-steered delivery (program attached, `sk_select_reuseport` pins the flow).
  - col B — kernel-hash-fallback delivery (program detached via `KernelFanout.DetachProgram`, so the 4-tuple hash drives — the SAME test harness, program attached = A, detached = B, the ONLY delta is the attach).
  Assertion: col A is NOT slower than col B at `-cpu=32 -benchtime=3s -count=3` on the c8g box (the SCISSORS rule: a 4c/16c number is NOT interchangeable with 32c). If col A is SLOWER, the bench t.Fatalf's with an honest NEGATIVE ("eBPF steering slower than hash fallback at 32c — Gap-3 NEGATIVE").
